# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

This repo contains two independently versioned applications plus a requirements doc:

- `erp backend/erp backend/` — ASP.NET Core (.NET 10) Web API, single project (`erp_backend`), EF Core + SQL Server.
- `erp/` — Angular 22 SPA (standalone components, PrimeNG UI, Vitest for unit tests).
- `Accounting_Software_SRS.md` — the product SRS (Chart of Accounts, Vouchers, Ledgers, Reports modules). Useful for understanding intended business rules (double-entry validation, voucher approval workflow, immutability of posted vouchers, etc).

## Commands

### Backend (`erp backend/erp backend/`)

```bash
dotnet build                              # build
dotnet run                                 # run (Development launches Swagger at /swagger, auto-migrates DB, seeds dev users)
dotnet ef migrations add <Name>            # add a migration after model changes
dotnet ef database update                  # apply pending migrations to the local DB
```

There is no backend test project (`*.Tests.csproj`) in this repo currently.

Connection string / JWT settings live in `appsettings.json` (`ConnectionStrings:DefaultConnection`, `Jwt:*`). Default dev DB is SQL Server on `localhost`, database `erp`.

Dev-seeded users (created on first run against a fresh DB, see `Program.cs`):
- `admin` / `Admin@123` — tenant Admin, Default tenant/branch (Id 1).
- `superadmin` / `SuperAdmin@123` — `SystemAdmin`, cross-tenant.

### Frontend (`erp/`)

```bash
npm start        # ng serve, http://localhost:4200
npm run build     # ng build
npm test          # ng test (Vitest)
```

`environment.development.ts` / `environment.ts` under `src/environments/` set `apiUrl` (points at the backend's HTTPS launch profile, `https://localhost:7002` by default — see `Properties/launchSettings.json`).

## Backend architecture

**Feature-folder-per-domain, not layered-by-type.** Each business domain (`Accounts/`, `CostCenters/`, `Vouchers/`, `Tenants/`, `Branches/`, `Users/`, etc.) owns its own `I<X>Repository` / `<X>Repository` and a `Dtos/` subfolder; `Controllers/` holds only thin ASP.NET Core controllers that delegate to a repository and wrap results in `ApiResponse<T>` (`Models/ApiResponse.cs`). A generic `Repositories/IRepository<T>` / `Repository<T>` wraps plain CRUD over `AppDbContext` and is used directly by simpler entities; feature-specific repositories are used where custom queries/validation are needed.

Every controller action follows the same try/catch shape: catch `AppException` subtypes (`Exceptions/AppExceptions.cs`: `NotFoundException`, `BadRequestException`, `UnauthorizedAppException`, `ForbiddenException`) and map to their `StatusCode`, catch everything else as a 500. User-facing strings are centralized in the `ResponseMessage` enum (`Messages/ResponseMessage.cs`) with `[Description]` attributes and formatted via `.ToText(args)` — add new messages there rather than inlining strings.

`Data/AppDbContext.cs` is the single `DbContext`; all entity configuration is Fluent API in `OnModelCreating` (no data annotations except `[Timestamp]` on `VoucherHeader.RowVersion`). Migrations are hand-verified, not blindly trusted from `dotnet ef migrations add` output — EF's autogenerated `defaultValue` for new non-nullable columns is often wrong for backfilling existing rows (see the tenancy migrations, where `defaultValue: 0`/`false` had to be corrected to the real default before applying).

### Multi-tenancy / multi-branch model

The system is multi-tenant: one **Tenant** (company) has many **Branches**; a **User** belongs to exactly one Tenant and is granted access to specific Branches via the `UserBranch` join table. This is enforced end-to-end, not just at the UI layer:

- `Models/Abstractions/ITenantScoped` / `IBranchScoped` are marker interfaces (`TenantId` / `TenantId`+`BranchId` props). Master/reference data (`Account`, `CostCenter`, `TaxRate`, `FiscalPeriod`, `User`, `AuditLog`) is tenant-scoped only — the Chart of Accounts and fiscal calendar are shared across a tenant's branches. Transactional data (`VoucherHeader`/`Detail`/`Attachment`, `BankStatementLine`, `RecurringVoucherTemplate(Line)`, `Budget`, `ReportSchedule`) is branch-scoped.
- `AppDbContext.OnModelCreating` applies EF Core global query filters to every entity implementing these interfaces via a **reflection loop** (not hand-written per entity) — implementing `ITenantScoped`/`IBranchScoped` on a new entity is enough to get automatic scoping, no `OnModelCreating` edit needed.
- `AppDbContext.SaveChanges(Async)` is overridden to auto-stamp `TenantId`/`BranchId` on inserted entities from the ambient `ICurrentTenantContext`, and to reject attempts to change those fields on existing rows. The stamp only fires when the field is still `0`, so code that explicitly sets `TenantId` (dev seeding, `SystemAdmin` cross-tenant creation) is never overwritten.
- `Tenant`, `Branch`, `UserBranch` themselves are **not** filtered (they define the scope, not get scoped by it) — any repository code querying them directly must apply its own `.Where(x => x.TenantId == ...)` when the caller isn't a `SystemAdmin`.
- Request-scoped tenant/branch resolution: the JWT carries a `tenant_id` claim (fixed per session). The *current branch* is **not** in the JWT — it's resolved per-request from an `X-Branch-Id` header, validated against `UserBranch` by `Middleware/BranchContextMiddleware` (registered between `UseAuthentication` and `UseAuthorization`), and stored in the scoped `Auth/ICurrentTenantContext`. This lets a client switch branches without re-authenticating and support multiple branches open in different tabs.
- Roles (`Auth/AppRoles`): `User`, `Admin` (tenant admin, scoped to their own tenant), `SystemAdmin` (cross-tenant — manages `Tenants`/`Branches`/`Users` controllers, bypasses tenant filters via `.IgnoreQueryFilters()` where needed). Only a `SystemAdmin` may assign the `SystemAdmin` role to a user; this is enforced in `Users/UserRepository`, not just at the controller/route level.
- Login (`Auth/AuthRepository`) necessarily bypasses the tenant filter (`IgnoreQueryFilters()`) since a username must be resolved before any tenant context exists; `Username` is globally unique across all tenants by design (no separate "company code" step at login).

⚠️ **Frontend gap**: the Angular app does not yet have a branch-selector UI or an interceptor that sends `X-Branch-Id` — `LoginResponse` already returns `tenantId`/`tenantName`/`branches[]`, but `core/auth/auth.service.ts` doesn't consume them yet. Any work on branch-scoped features (vouchers, ledgers, reports) from the frontend needs that wiring first.

## Frontend architecture

Angular 22 standalone components (no NgModules), PrimeNG (Aura theme) for UI. Structure:
- `src/app/core/<feature>/` — one service + models file per domain (e.g. `core/auth/`, `core/vouchers/`), consumed via `inject()`.
- `src/app/layout/{shell,topbar,sidebar,body}` — the authenticated app shell.
- `src/app/pages/<feature>/` — routed page components, one folder per route.

Auth state (`core/auth/auth.service.ts`) is the canonical pattern for client-side state in this app: a private `signal<T | null>` backed by `localStorage`, exposed via read-only `computed()` accessors, mutated only through a private setter called from the service's own API calls. Follow this shape for any new cross-cutting client state (e.g. the branch-context service the frontend gap above would need).

`core/auth/auth.interceptor.ts` (functional `HttpInterceptorFn`) attaches the bearer token and force-logs-out on 401; `core/auth/auth.guard.ts` (functional `CanActivateFn`) gates the `Shell` route tree in `app.routes.ts`.
